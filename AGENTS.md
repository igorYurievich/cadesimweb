# Правила для ИИ-агентов (Codex, Claude и др.)

Этот файл читай перед любой работой над проектом. Следуй ему, если пользователь прямо не попросил иного.

## О проекте

**CADe SIMU Web** — веб-редактор электрических схем и симулятор релейной логики (аналог CADe SIMU).
Стек: TypeScript (strict), Vite, Vitest. Внешних runtime-зависимостей нет.
Владелец — вайбкодер: код читает редко, поэтому результат нужно проверять командами, а не «на глаз».

## Структура

- `src/model/` — модель схемы, каталог компонентов, чтение и запись формата `.cad`.
- `src/engine/` — движок симуляции. Чистая функция «схема + ввод → состояние». **Никакого DOM, localStorage и браузерных API.**
- `src/ui/` — интерфейс: холст, палитра, вкладки, меню, экспорт, переводы (`i18n/`).
- `src/data/` — каталог команд (`components.json`) и примеры схем (`examples/Ejemplos/`, `examples/Ejemplos 2/`).
- `tests/` — автотесты Vitest и фикстуры `.cad` в `tests/fixtures/`.
- `FORMATO_CAD.md` — описание формата `.cad`. Читай перед любыми правками импорта/экспорта.

Алиасы импортов: `@engine/*`, `@model/*`, `@ui/*`.

## Команды

```bash
npm ci               # установка зависимостей
npm run dev          # сервер разработки
npm run typecheck    # проверка типов
npm test             # все тесты
npm run build        # проверка типов + сборка
```

**Перед тем как сказать «готово», обязательно запусти `npm run typecheck`, `npm test` и `npm run build`.**
Все три должны проходить без ошибок. Если что-то упало, исправь причину; не отключай и не удаляй тесты, чтобы «позеленело».

## Ограничения на размер кода

- Файл — не длиннее **300 строк**. Если растёт больше, разбей по смыслу на модули.
- Строка — не длиннее **120 символов**. Длинные вызовы с кучей аргументов переноси по одному аргументу на строку.
- Функция — не длиннее **60 строк**. Огромные функции с замыканиями (как раньше `mountApp`) не создавай.
- Одна ответственность на файл: имя файла должно честно говорить, что в нём лежит.

## Стиль кода

- Строгий TypeScript. Не используй `any`, `as any` и `@ts-ignore`; если без этого никак, объясни почему в комментарии.
- Окончания строк — **LF**, кодировка UTF-8.
- Не оставляй мёртвый код, закомментированные куски, `console.log` и `TODO` без причины.
- Комментарии на русском, коротко и про «зачем», а не «что».
- Не дублируй код: сначала поищи подходящую функцию в проекте.
- Не добавляй новые зависимости (`npm install`) без явной просьбы пользователя.

## Что нельзя ломать

1. **Ключи localStorage и формат сохраняемых данных** (`AUTOSAVE_KEY`, `BETA_NOTICE_KEY` и другие в `src/ui/constants.ts`). Иначе у пользователей пропадут сохранённые схемы.
2. **Формат `.cad`**: импорт и экспорт должны оставаться совместимыми с CADe_SIMU 4.x. Тесты с фикстурами в `tests/fixtures/` — эталон.
3. **Движок симуляции** (`src/engine/`) покрыт сценарными тестами на реальных учебных схемах. Любая правка движка требует прогона всех тестов.
4. **Публичный вход** `mountApp(root)` в `src/ui/app.ts` и `src/main.ts`.

## Как работать

1. Сначала изучи нужные файлы и найди, где уже решается похожая задача.
2. Делай **минимальные изменения** под задачу. Не трогай несвязанный код и не «улучшай заодно».
3. Рефакторинг и новые функции не смешивай: если задача — рефакторинг, поведение приложения менять нельзя.
4. Для новой логики (особенно в `engine/` и `model/`) добавляй тесты в `tests/`. Для работы с localStorage используй in-memory мок, а не настоящий браузер.
5. Если задача неясна или требует решения, которое меняет поведение приложения, задай уточняющий вопрос, а не угадывай.

## Новые компоненты и переводы

- Новый компонент добавляй в каталог (`src/model/catalog.ts`, `src/data/components.json`) и в таблицу поведения движка (`src/engine/behaviors.ts`), затем покрой тестом.
- Тексты интерфейса добавляй сразу во все языки в `src/ui/i18n/`: `es`, `en`, `it`, `ru`, `fr`, `ar`. Нельзя оставлять ключ только в одном языке.
- Примеры схем кладут в `src/data/examples/Ejemplos/`. Не создавай копии файлов в других папках.

## Итоговый отчёт

В конце работы кратко напиши (простым языком, без лишнего жаргона):
- что сделано и в каких файлах;
- результаты `typecheck`, `test`, `build`;
- что стоит проверить вручную в браузере (если менялся интерфейс);
- что намеренно не делалось или осталось на потом.
